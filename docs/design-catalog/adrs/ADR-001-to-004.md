# ADR-001: Centralized GitLab CI templates (industrialized DevSecOps)

## Status
Accepted

## Context
ITNET’s accompaniment guide contrasts duplicated per-microservice pipelines (drift, forgotten controls) with a central `ci-templates` project. `backend-jarvis` already uses GitLab Auto-DevOps stages and secret detection.

## Decision
Use a dedicated GitLab project `<group>/ci-templates` as the single source of truth for security, build, container, deploy, and DAST jobs. Each service keeps a minimal `.gitlab-ci.yml` that sets service variables and `include:`s templates by ref.

## Alternatives Considered
- **Per-repo full pipelines** — fast to start, high drift.
- **GitHub Actions reusable workflows** — wrong SCM for ITNET GitLab.
- **Harness STO/CD only** — strong patterns, but adds vendor and dual-CI cost.

## Consequences
- Positive: homogeneous gates, one place to raise Semgrep/Trivy policies, fast onboarding of new services.
- Negative: template changes can break all consumers — require versioned refs (`ref: v1.x`) and changelog.
- Trade-off: platform ownership of templates vs app-team freedom.

# ADR-002: Wayhost KVM1 + Docker Compose (not k3s)

## Status
Accepted

## Context
Production/demo target is a Wayhost **KVM1**: Ubuntu, **1 vCPU**, **4 GB RAM**, **50 GB** disk (actif through 3 sept. 2026). Cloud remains Wayhost-only.

## Decision
- **Runtime:** **Docker Compose** + lightweight edge (**Caddy** preferred) on the KVM1 VPS.
- **Reject k3s** on this plan (needs ~2 CPU / ~1.5 GB control-plane class footprint; starves the app on 1 vCPU / 4 GB).
- **Images:** GitLab Container Registry; VPS only pulls — never builds.
- **Heavy tools off-box:** all SAST/SCA/DAST/runners; DefectDojo remote.
- **Static sites:** Prefer Wayhost **Hosting Cloud** to save VPS RAM.
- **IaC:** Ansible baseline (Docker, UFW, Caddy, logrotate, prune); Terragrunt optional wrappers.

## Alternatives Considered
- **k3s** — deferred until ≥2 vCPU / 8 GB.
- **Hosting Cloud only** — OK for static vitrines; insufficient for custom API containers.
- **Traefik with many middlewares** — heavier; use Caddy/nginx unless weighted canary is essential.

## Consequences
- Positive: ~2–3 GB usable for the app; fast deploys; simple rollback by image digest.
- Negative: no K8s ecosystem (Helm/operators); canary must be RAM-aware (short-lived tiny replica).
- See [capacity-kvm1.md](../capacity-kvm1.md) for hard memory/disk budgets.

# ADR-003: Rolling-first delivery on KVM1; sequential blue-green; light canary

## Status
Accepted

## Context
Harness progressive delivery still applies, but dual full-size replicas on 4 GB cause OOM. 1 vCPU cannot absorb control-plane + two apps.

## Decision
| Environment / risk | Strategy on KVM1 |
|--------------------|------------------|
| Default / day-to-day | **Rolling**: recreate one container; healthcheck; keep previous digest for instant rollback |
| Major cutover | **Sequential blue-green**: start new → flip → **stop old immediately** |
| Optional soak | **Light canary**: ≤512 MB canary, 5–10% traffic, ≤5 min, then promote or kill |

Skip long multi-step 2→25→50→100% canaries unless the app `mem_limit` is small enough that stable+canary ≤ ~2 GB combined.

## Alternatives Considered
- **Always-on dual replicas** — rejected on KVM1.
- **k3s + Argo Rollouts** — rejected until larger VPS.
- **DNS TTL flip** — slow; prefer local Caddy upstream switch.

## Consequences
- Positive: safe rollback without doubling steady-state RAM.
- Negative: brief overlap only during cutover; must automate stop-old step.

# ADR-004: Security control stack (shift-left + evidence)

## Status
Accepted

## Context
ITNET five controls + Medium secure pipeline (secrets, MFA/repo hygiene, Vault on VPS / GitLab vars, SCA lock, compose policy, post-deploy monitoring, KPIs).

## Decision
| Control | Primary tools |
|---------|---------------|
| Secrets | Gitleaks + GitLab Secret Detection |
| SAST | Semgrep (pilot) → SonarQube if quality gate needed |
| SCA / image / SBOM | Trivy |
| IaC / K8s policy | Checkov/tfsec + Kyverno/OPA Gatekeeper |
| DAST | OWASP ZAP |
| Aggregation | DefectDojo |
| Runtime | Wayhost metrics + optional Prometheus/Grafana on VPS |
| Secrets runtime | GitLab Masked/Protected + host env (optional Vault on VPS) |

Critical findings **block** deploy; non-critical **warn** and track. Reports retained as CI artifacts.

## Consequences
- Positive: matches workshop checklist; clear remediation loop.
- Negative: false positives — tune rules or teams abandon gates (ITNET §8).

# ADR-005: DefectDojo remote findings hub (not on KVM1)

## Status
Accepted

## Context
Design catalog tracks findings in DefectDojo. The Wayhost KVM1 has 4 GB RAM; DefectDojo (Django + Postgres + Redis + Celery) would starve the Flo app.

## Decision
- Run DefectDojo on a **remote** host (Mac, second VPS, or ITNET shared instance).
- CI job `defectdojo_import` reimports scan artifacts via `/api/v2/reimport-scan/` with `auto_create_context`.
- Job is optional: skipped unless `DEFECTDOJO_URL` and `DEFECTDOJO_API_TOKEN` are set (keeps pipelines green).

## Alternatives Considered
- DefectDojo on KVM1 — rejected (capacity).
- GitLab Security Dashboard only — OK short-term; weaker cross-tool aggregation for the workshop story.

## Consequences
- Positive: full ITNET findings loop without risking demo OOM.
- Negative: team must host/reach a Dojo URL from the runner.
